# Достаточность данных для аналитики

Backend возвращает отдельные сигналы достаточности данных для разных аналитических областей.
Это не общий рейтинг, не медицинская оценка и не вывод о качестве поведения пользователя.
Контракт нужен, чтобы analytics, adaptive nutrition и будущий AI Coach не делали сильных
выводов из пустых или редких наблюдений.

## API-контракт

`GET /api/v1/workouts/progress/summary` и соответствующие trainer endpoints возвращают
`data_sufficiency` со следующими областями:

- `nutrition_coverage` — заполненные прошлые дни дневника;
- `weight_trend` — точки веса и длительность между первой и последней точкой;
- `anthropometry` — достаточность хотя бы одной окружности тела;
- `workout_logging` — полнота записанных базовых рабочих подходов в завершённых тренировках;
- `working_sets` — число учтённых рабочих подходов и тренировочных сессий;
- `rir_coverage` — отдельная полнота необязательных значений «повторы в запасе»;
- `schedule_adherence` — наличие тренировок, которые уже можно учитывать в соблюдении плана.

`GET /api/v1/workouts/progress/training-analytics` и trainer endpoint этой аналитики возвращают
тот же `ruleset_version`, но только связанные с тренировками области: `workout_logging`,
`working_sets` и `rir_coverage`.

Каждый сигнал содержит:

- `status`: `sufficient`, `limited` или `insufficient`;
- `counters`: фактические значения и применённые пороги;
- `reason_keys`: стабильные machine-readable причины, включая `thresholds_met` для достаточных
  данных.

Текущая версия правил — `data-sufficiency-v1`. Клиентский интерфейс не должен показывать
reason keys как готовый пользовательский текст: для человека нужны понятные русские формулировки.

## Детерминированные product rules

Пороги задают минимальное количество наблюдений для осторожной продуктовой интерпретации. Они не
являются медицинскими нормами, не доказывают причинность и не оценивают здоровье.

| Область | `insufficient` | `limited` | `sufficient` |
| --- | --- | --- | --- |
| Питание | Нет ни одного заполненного прошлого дня | Есть данные, но заполнено меньше требуемого числа дней | Заполнено 7 прошлых дней; для периода 7 дней достаточно всех 6 доступных прошлых дней |
| Вес | Нет точек | Есть точки, но меньше 3 или интервал короче 14 дней | Не меньше 3 точек за интервал не короче 14 дней |
| Антропометрия | Нет ни одной окружности | Окружности есть, но ни одна не достигла 3 точек и 14 дней | Хотя бы одна окружность достигла 3 точек и 14 дней |
| Полнота журнала тренировки | Нет завершённых тренировок, предписанных подходов или базовых рабочих подходов с записанными повторами | Повторы записаны только для части предписанных подходов | Для завершённых тренировок повторы записаны во всех предписанных базовых рабочих подходах |
| Рабочие подходы | Нет учтённых рабочих подходов | Меньше 6 подходов или меньше 2 тренировочных сессий | Не меньше 6 подходов минимум в 2 сессиях |
| Повторы в запасе | Нет рабочих подходов либо нет ни одного значения | Есть значения, но меньше 3 или покрытие ниже 50% рабочих подходов | Не меньше 3 значений и покрытие не ниже 50% |
| Расписание и соблюдение плана | Нет тренировок, которые уже можно оценить | Можно оценить 1–2 тренировки | Можно оценить не меньше 3 тренировок |

Для питания текущий день исключён, потому что дневник ещё может быть не завершён. Поэтому
`eligible_day_count` равен `period_days - 1`. Для 30- и 90-дневного периода достаточность
наступает после 7 заполненных дней; остальные дни всё равно отражаются в factual coverage.

Для `workout_logging` дроп-сеты не закрывают пропущенные предписанные подходы: полнота считается
по обычным рабочим подходам с записанными повторами и старым строкам без `set_kind`, а число
аналитических рабочих подходов включает также дроп-сеты. Разминочные и незавершённые подходы не
учитываются.

RIR остаётся необязательным. Его отсутствие влияет только на `rir_coverage` и не понижает
`workout_logging` или `working_sets`. Из достаточного RIR-покрытия нельзя выводить усталость,
готовность, восстановление или близость к отказу сверх фактически записанной категории.

## Периоды, права и отсутствующие данные

Счётчики рассчитываются только внутри запрошенного периода `7`, `30` или `90` дней в локальном
календаре аккаунта. Статус может отличаться между периодами без изменения исходных данных.

User endpoints используют identity авторизованного аккаунта. Trainer endpoints возвращают тот же
контракт только при действующей связи с клиентом и наследуют существующие server-side проверки.
Посторонний или бывший тренер получает `404`; отдельного обходного endpoint для sufficiency нет.

`insufficient` не преобразуется в ноль аналитической метрики, а `limited` не запрещает показывать
фактические значения. Эти статусы ограничивают только силу последующего вывода. Ни один сигнал не
объединяется в единый confidence score.
