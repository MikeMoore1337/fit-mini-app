# История ориентиров КБЖУ

## Канонический контракт

Каждая версия суточных ориентиров калорий, белков, жиров и углеводов хранится в
`nutrition_targets`. Период версии полуоткрытый: `[effective_from, effective_to)`. Поэтому цель
действует в `effective_from`, но уже не действует в `effective_to`.

Для пользователя существует не больше одной открытой версии (`effective_to IS NULL`). Сохранение
новой цели блокирует строку пользователя в транзакции, закрывает текущую версию и связывает её с
новой через `superseded_by_id`. Одинаковый повтор запроса в ту же дату возвращает уже созданную
версию. Изменение значений в ту же дату сохраняет предыдущую запись как версию нулевой длительности:
она остаётся в аудиторской истории, но не действует ни в один календарный день.

Разрешённые источники:

- `calculated` — подтверждённый результат калькулятора пользователя;
- `manual` — значения, введённые пользователем без пересчёта;
- `trainer` — назначение действующего тренера своему клиенту;
- `adaptive` — явно принятое пользователем предложение адаптивной калибровки.

`created_by_user_id` реализован существующим FK `assigned_by_user_id`, а `created_at` — существующим
локальным timestamp `saved_at`. API возвращает канонические и совместимые legacy-поля из одного
источника, без дублирования значений в БД.

## Даты, история и конфликт изменений

Дата начала интерпретируется в IANA-часовом поясе владельца цели. Будущая дата запрещена. Новая дата
не может быть раньше `effective_from` текущей открытой версии: уже закрытая история не переписывается
задним числом. В пределах текущего периода последнее подтверждённое self/trainer изменение становится
новой открытой версией; источник и автор всегда видимы пользователю.

Существующая single-row цель мигрируется как `calculated` с `effective_from = DATE(saved_at)`. Более
ранняя история не выдумывается. Calculator context может быть `NULL` у первой ручной цели; точные
введённые КБЖУ при этом остаются полными и пригодными для дневника и отчётов.

## Ручная проверка энергии

Справочная энергия вычисляется детерминированно как `protein_g * 4 + fat_g * 9 + carbs_g * 4`.
Порог заметного расхождения — большее из `100 ккал` и `10%` указанной калорийности. Это product
heuristic для обнаружения вероятной ошибки ввода с запасом на округление и различия маркировки, а не
медицинская норма. При превышении порога пользователь должен явно подтвердить сохранение; backend
повторяет ту же проверку и хранит исходные значения без silent correction.

## Потребители и lifecycle

- Today, дневник и trainer workspace читают одну открытую версию.
- Progress/adherence выбирает версию по дате каждого заполненного дня; день без effective target не
  превращается в ноль и не входит в denominator соблюдения цели.
- Принятое adaptive proposal создаёт `source=adaptive`, а не изменяет строку на месте.
- Account export schema v2 сохраняет совместимое поле `nutrition` для текущей версии и полный список
  `nutrition_target_history`.
- Удаление аккаунта удаляет принадлежащую пользователю историю каскадно. При удалении автора у чужих
  версий author FK очищается, но сами значения и периоды клиента сохраняются.

Активный тренер может создавать и читать версии только для своего клиента. После прекращения связи
новые записи и доступ к trainer endpoint истории запрещены server-side; видимость controls во
frontend не является границей авторизации.
