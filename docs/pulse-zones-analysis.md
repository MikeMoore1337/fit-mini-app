# Анализ расчёта пульсовых зон

## Текущая реализация

- Профиль хранится в `user_profiles`; возраст выводится из nullable-поля
  `birth_date`, выбранная цель хранится в `goal`, ЧСС покоя в модели отсутствует.
- Backend-функция `calculate_tanaka_heart_rate_zones` находится в
  `backend/fitminiapp_api/services/profile.py`. Она считает максимальную ЧСС по
  формуле Танаки и пять зон 50–100% от максимальной ЧСС.
- Endpoint `/api/v1/me` вызывает backend-функцию и возвращает
  `estimated_max_heart_rate` и `heart_rate_zones` внутри профиля.
- Frontend дублирует тот же расчёт в
  `frontend/src/features/profile/heartRateZones.ts`; `ProfileForm` показывает
  локально рассчитанные значения вместо результата API.
- Веб-версия и Telegram Mini App используют один React entry point, страницу
  `MiniAppPage` и компонент `ProfileForm`. Отдельной реализации формул для
  Telegram нет.

## Связанные данные и контракты

- Идентификаторы целей уже едины и подходят задаче: `fat_loss`,
  `recomposition`, `maintenance`, `muscle_gain`.
- Обновление профиля проходит через `UserProfileUpdate`, сервис
  `update_profile` и `PATCH /api/v1/me/profile`.
- Изменения цели, роста, веса и частоты тренировок синхронизируются с текущей
  моделью КБЖУ. Пульсовые зоны напрямую в расчёте КБЖУ не участвуют.
- Контракт frontend генерируется из OpenAPI в
  `frontend/src/shared/api/schema.d.ts`.
- Последняя миграция Alembic — `0030_local_credentials`; добавление сохраняемой
  ЧСС покоя требует новой nullable-колонки и безопасной миграции.

## Тесты

- Frontend unit-тест существующего локального расчёта находится в
  `frontend/tests/unit/features/profile/heartRateZones.test.ts`.
- Backend интеграционные тесты профиля находятся в
  `backend/tests/test_app.py`; отдельного unit-теста доменной логики пульса нет.
- Playwright покрывает общий интерфейс приложения в
  `frontend/tests/e2e/app.spec.ts`, включая профиль и адаптивную проверку.

## Решение для следующих этапов

1. Сделать backend единственным источником расчёта: выделить чистые функции
   Танаки, Карвонена, физиологических зон и рекомендации по цели в сервисе
   профиля, включая единое округление половин вверх.
2. Расширить ответ профиля готовым результатом и признаком персонализации;
   frontend не должен повторять формулы.
3. Добавить nullable `resting_heart_rate` в профиль, API-схемы и миграцию с
   валидацией 30–120 и проверкой относительно расчётной максимальной ЧСС.
4. Обновить общий `ProfileForm`, поэтому одинаковый результат автоматически
   будет доступен и в браузере, и в Telegram Mini App.
5. Существующую логику КБЖУ и оценки интенсивности кардио не менять.
