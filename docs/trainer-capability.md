# Прямое включение режима тренера

## Контракт capability

`Trainer` — независимая возможность authenticated-аккаунта, а не исключающая роль. Пользователь
сохраняет личный профиль, программы, тренировки, питание и прогресс. `Admin` и `Trainer` не
назначаются друг из друга автоматически.

Пользователь включает режим из Profile после принятия кратких условий через
`POST /api/v1/me/trainer-capability`. Повторный запрос идемпотентен: capability остаётся активной,
а повторное audit-событие не создаётся. Backend записывает только `source` и версию условий, без
пользовательского текста или данных клиента. `GET /api/v1/me/trainer-capability` возвращает
актуальные счётчики активных клиентов и ожидающих приглашений для guard UI.

Режим не означает проверку образования, сертификации или профессиональной квалификации, не
создаёт публичный профиль, оплату или маркетплейс. Доступ к данным клиента появляется только после
его подтверждения и повторно проверяется backend по активной связи.

## Отключение

`DELETE /api/v1/me/trainer-capability` разрешён только при отсутствии активных клиентов. При
активной связи backend возвращает `409`; пользователь сначала завершает отношения с каждым
клиентом. Это исключает неявное прекращение доступа и сохраняет понятный жизненный цикл данных.

При безопасном отключении ожидающие приглашения отзываются, но завершённые отношения, программы,
тренировки и комментарии не удаляются. Повторное отключение идемпотентно. Создание и принятие
приглашения синхронизированы с изменением capability блокировкой server-side owner row, поэтому
новая связь не может появиться между guard-проверкой и отключением.

## Решение по legacy applications и миграции

Новая schema migration не нужна: каноническим persistent state остаётся существующий
`users.is_coach`. Таблица `coach_role_applications` не удаляется и не переписывается, потому что в
ней может находиться production history, включённая в account export и delete lifecycle. Её строки
после cutover являются read-only legacy history; старые `pending` сохраняют фактический статус на
момент отключения workflow и не трактуются как действующая очередь.

Пользовательские и административные application/review endpoints, Profile application UI и вкладка
модерации удалены из активного продукта. Отдельных application-specific notifications в текущей
реализации не было, поэтому data migration или массовая отмена уведомлений не требуется.

## Проверка и границы

Каноническая авторизация coach endpoints остаётся в `require_coach`; frontend visibility не является
security boundary. Browser и mocked TMA используют один React flow. Реальные Telegram Android/iOS
проверки фиксируются отдельно и не подменяются viewport-эмуляцией.
