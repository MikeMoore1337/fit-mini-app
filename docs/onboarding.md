# Постепенное знакомство пользователя с продуктом

Первый запуск Web, mobile Web и Telegram Mini App использует один и тот же flow на
`/onboarding`. После успешной авторизации новый пользователь, открывающий `/app`, попадает туда
до основного приложения. Уже завершивший минимальный шаг пользователь открывает `/app` напрямую.

## Контракт состояния

`GET /api/v1/me` и ответ `PATCH /api/v1/me/profile` содержат объект `onboarding`:

```json
{
  "status": "required",
  "required_fields": ["goal"],
  "missing_fields": ["goal"]
}
```

Состояние вычисляется из основной модели `UserProfile`; отдельной модели для onboarding или
профиля нет. Сейчас обязательно только поле `goal`. Канонические значения:
`fat_loss`, `muscle_gain`, `maintenance`, `recomposition`.

Возраст, рост, вес, пол, активность и параметры тренировок не являются блокером первого запуска.
Они запрашиваются в контексте расчёта питания или подбора программы. Уже сохранённые цель,
дата рождения, рост и вес используются для начального заполнения личного расчёта питания.

После сохранения цели пользователь выбирает одно действие: открыть «Сегодня», настроить питание
или подобрать программу. Выполнять все сценарии последовательно не требуется. Обновление страницы
повторно показывает выбор действия, а безопасный `next` сохраняет разрешённое продолжение.

## Контракт событий активации

Frontend публикует события через единый privacy-safe контракт `yfc:product-event`. Подробная
карта продуктовой аналитики хранится в owner-only документации и не входит в публичный Git.
Текущая реализация ничего не отправляет во внешний сервис.

Поддерживаемые события:

- `onboarding_started`;
- `onboarding_completed`;
- `onboarding_next_action_selected` с `next_action`: `today`, `nutrition`, `programs` или
  `continuation`.

Каждое событие содержит только `surface` (`web` или `telegram`) и безопасный системный envelope.
В события нельзя добавлять цель, возраст, рост, вес, пол, user ID или другие значения профиля и
питания.
