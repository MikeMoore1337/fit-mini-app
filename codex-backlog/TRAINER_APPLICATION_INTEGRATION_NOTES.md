# Trainer application integration notes

## Решение для первого релиза

Заявка нужна для ручного открытия кабинета тренера, а не для подтверждения профессиональной квалификации.

Целевой сценарий:

```text
Пользователь
-> подаёт короткую заявку
-> заявка получает статус pending
-> Root или super_admin рассматривает её вручную
-> approve атомарно активирует Trainer capability
-> пользователь получает уведомление и видит Coach workspace
```

## Основные инварианты

- Trainer application и Trainer capability - разные сущности.
- Заявка хранит историю подачи и решения.
- Capability определяет текущий фактический доступ к Coach workspace и trainer API.
- Одобрение заявки не делает пользователя профессионально верифицированным тренером.
- В интерфейсе и публичных материалах нельзя использовать формулировки `проверенный тренер`, `сертифицированный тренер` или аналогичные утверждения без отдельной реальной проверки.
- В первом релизе не загружаются дипломы, сертификаты, паспортные данные и иные документы.
- Trainer остаётся обычным пользователем с Personal functionality и дополнительно получает Coach context.
- Одобрение не создаёт trainer-client relationship и не открывает данные клиентов без принятого приглашения.
- AI Coach может объяснить сценарий и статусы, но не оценивает квалификацию, не принимает решение и не назначает capability.
- Demo Mode не отправляет реальные заявки и не создаёт persistent application records.

## Минимальная анкета

Использовать текущие verified account identities, не копируя без необходимости email или Telegram в отдельные поля заявки.

Поля заявки:

- опыт работы: `less_than_year`, `one_to_three`, `three_to_five`, `more_than_five`;
- направления работы - ограниченный список плюс `other`;
- как пользователь планирует применять приложение;
- примерное количество клиентов - необязательно;
- короткое описание о себе - необязательно или объединяется с intended use, если current UX показывает, что отдельное поле избыточно;
- согласие с правилами кабинета тренера.

Поля должны иметь разумные лимиты, нормализацию и понятные русские подписи. Не собирать медицинские данные, документы или данные клиентов.

## Статусы и переходы

```text
no application -> pending
pending -> approved
pending -> rejected
pending -> withdrawn
rejected -> new pending application
withdrawn -> new pending application
approved -> terminal historical decision
```

- У пользователя только одна активная `pending` заявка.
- Повторная отправка после recoverable network error не создаёт дубликат.
- Повторная подача создаёт новую запись, а не переписывает старое решение.
- `needs_changes` в первом релизе не нужен: администратор отклоняет заявку с понятной причиной, пользователь исправляет данные и подаёт новую.
- Активный Trainer не может подать новую заявку.
- Suspension/revocation Trainer capability не переписывает старую approved application.

## Права рассмотрения

Минимальные permissions:

- `trainer_applications.read`;
- `trainer_applications.manage`.

Целевая политика:

- Root и `super_admin` - read + manage;
- `support_admin` - read-only, без approve/reject и без доступа к внутреннему комментарию; backend использует отдельную безопасную read projection;
- обычный пользователь и Trainer без Admin - только собственная заявка;
- администратор не может одобрить или отклонить собственную заявку; Root при необходимости получает Trainer capability отдельным root-only assignment действием без создания фиктивной заявки.

## Порядок задач

```text
69  -> 69A -> 70 -> 70A -> 71 -> 71A -> 72
```

- `69A` создаёт доменную модель и пользовательский API поверх окончательной capability model.
- `70A` создаёт moderation API, атомарное решение, audit и capability orchestration.
- `71A` добавляет Profile UX, Admin Workspace queue, уведомления и activation onboarding.
- `72` адаптирует уже готовый пользовательский flow к Telegram Mini App. Admin Workspace остаётся Web-only.

## Не входит в первый релиз

- автоматическое решение через AI;
- профессиональная проверка документов;
- verified badge;
- публичный каталог или marketplace тренеров;
- рейтинг и отзывы;
- платная заявка;
- generic support messenger;
- апелляционный workflow внутри приложения;
- автоматическое создание клиентов или доступ к чужим данным.
