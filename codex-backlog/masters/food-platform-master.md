# Задача для Codex: развитие Your Fitness Coach в единый фитнес-сервис

## Контекст

Репозиторий:

`https://github.com/MikeMoore1337/fit-mini-app`

Продакшен-сайт:

`https://your-fitness-coach.ru/`

Проект уже работает как единый сервис для браузера и Telegram Mini App и включает:

- профиль пользователя;
- цели и параметры активности;
- тренировочные программы;
- расписание;
- выполнение тренировок;
- фиксацию подходов, повторений и рабочего веса;
- историю тренировок;
- личные рекорды;
- отслеживание веса и других параметров тела;
- расчёт КБЖУ;
- уведомления;
- инструменты тренера и работу с клиентами.

Текущий стек и существующую архитектуру необходимо изучить непосредственно в репозитории перед внесением изменений.

Цель следующего крупного этапа - развить существующий продукт в полноценный единый фитнес-сервис, который объединяет лучшие пользовательские идеи сервисов наподобие FatSecret и Fitness Online, но не копирует их код, дизайн, базы данных или закрытые материалы и не зависит от их платных API.

Ключевая продуктовая идея:

> питание + тренировки + прогресс + работа с тренером + единая аналитика в одном приложении.

Веб-приложение и Telegram Mini App должны остаться двумя способами использования одного продукта, а не превращаться в независимые приложения.

---

# 1. Главные ограничения

## 1.1. Не переписывать проект с нуля

Сначала провести аудит текущей реализации и определить:

- что уже реализовано;
- какие сущности и API уже существуют;
- какие компоненты можно переиспользовать;
- какие изменения требуют расширения текущих моделей;
- какие части можно реализовать без изменения существующих контрактов;
- какие миграции действительно необходимы.

Предпочитать эволюционное расширение существующей архитектуры.

Не выполнять большой рефакторинг только ради "красоты", если он не требуется для этой задачи.

## 1.2. Единый Web + Telegram Mini App

Не создавать отдельный второй frontend.

Должны оставаться общими:

- React/TypeScript-код приложения;
- бизнес-логика frontend;
- API;
- backend;
- PostgreSQL;
- модели данных;
- расчёты;
- питание;
- тренировки;
- аналитика;
- прогресс;
- компоненты, которые могут быть общими.

Допускаются platform-specific адаптеры для Web и Telegram Mini App.

Для Web допускаются:

- web-аутентификация;
- web-навигация;
- Web preference `system/light/dark` поверх общей YFC Light/Dark темы;
- desktop-компоновка;
- особенности браузера.

Для Telegram Mini App допускаются:

- Telegram-аутентификация;
- Telegram Mini Apps SDK;
- Telegram BackButton/MainButton и другие подходящие API;
- Telegram `colorScheme` как выбор общей YFC Light/Dark темы;
- переходы в бота;
- Telegram-уведомления;
- особенности viewport и safe area.

Web и Telegram Mini App используют одинаковые фирменные YFC Light/Dark colors и semantic tokens. Telegram-specific отличия относятся к platform behavior/shell, а не к отдельному дизайну.

Должны совпадать:

- структура продукта;
- дизайн-система компонентов;
- типографическая иерархия;
- размеры и типы кнопок;
- скругления;
- отступы;
- логика карточек;
- поведение форм;
- общие UX-паттерны.

Desktop-версия может использовать пространство шире и показывать больше информации одновременно.

Mobile Web и Telegram Mini App должны эффективно использовать маленький экран и при одинаковом viewport использовать одну mobile visual composition, кроме documented platform-specific safe-area/navigation/runtime differences.

# 2. Финансовое ограничение

Проект должен иметь возможность работать без обязательных сторонних платных сервисов.

## Обязательное правило

Не добавлять функциональность, без которой приложение перестанет нормально работать после:

- окончания trial;
- исчерпания бесплатной квоты;
- введения платного тарифа сторонним сервисом;
- недоступности внешнего API.

Не использовать обязательные платные API.

Если используется внешний бесплатный или открытый источник данных:

- он должен быть скрыт за собственным adapter/service layer;
- отказ источника не должен ломать основное приложение;
- должен существовать локальный fallback;
- бизнес-логика не должна зависеть от формата ответа конкретного поставщика;
- необходимо проверить условия использования и лицензию по официальной документации.

FatSecret API не делать обязательной зависимостью проекта.

FatSecret и Fitness Online использовать только как продуктовые ориентиры для UX и набора возможностей.

Не копировать:

- их код;
- закрытые API;
- дизайн один в один;
- тексты;
- иллюстрации;
- базы данных;
- защищённые материалы.

# 3. ИИ-ассистент сейчас не реализовывать

ИИ-ассистент будет отдельной задачей.

На этом этапе:

- не подключать LLM API;
- не добавлять платные AI API;
- не строить чат;
- не внедрять RAG;
- не добавлять AI-зависимости.

Но архитектуру данных проектировать так, чтобы в будущем ИИ-ассистент мог безопасно получать агрегированный контекст пользователя через внутренний API/service layer:

- цели;
- тренировочную историю;
- питание;
- прогресс;
- соблюдение плана;
- текущие рекомендации.

Не создавать AI-specific инфраструктуру заранее без необходимости.

# 4. Целевая структура продукта

Проверить текущую навигацию и предложить минимально разрушительное развитие к следующей структуре.

Основные пользовательские разделы:

1. Сегодня
2. Тренировки
3. Питание
4. Прогресс
5. Тренер
6. Профиль

Для тренера дополнительно должны быть доступны существующие инструменты управления клиентами и связанные с ними новые данные питания/прогресса.

Не менять навигацию механически только ради соответствия этому списку.

Сначала сопоставить его с текущей структурой и предложить наиболее естественную миграцию UX.

# 5. Раздел "Сегодня"

Нужен единый dashboard, который отвечает пользователю на вопрос:

> Что мне сегодня нужно сделать и как я двигаюсь к цели?

На одной странице должны быть доступны компактные карточки.

## Питание

- съеденные калории / целевые;
- белки / цель;
- жиры / цель;
- углеводы / цель;
- быстрый переход к добавлению еды.

## Тренировка

Если запланирована:

- название;
- время;
- количество упражнений;
- ориентировочная продолжительность, только если она может быть рассчитана без выдуманных данных;
- кнопка перехода к тренировке.

Если тренировки нет:

- корректное состояние "Сегодня тренировка не запланирована".

## Прогресс

- последний вес;
- изменение относительно предыдущего значения;
- краткий тренд за разумный период.

## План

После появления соответствующей логики:

- выполнение тренировок;
- выполнение кардио;
- соблюдение калорийности;
- соблюдение белка;
- общий показатель соблюдения плана.

Dashboard не должен превращаться в перегруженную аналитическую страницу.

Подробности должны открываться в соответствующих разделах.

---

# 6. Полноценный раздел "Питание"

Существующий расчёт КБЖУ оставить как основу целей питания, если он уже реализован корректно.

Над ним необходимо построить полноценный пищевой дневник.

## 6.1. Дневник дня

Пользователь выбирает дату и видит:

- завтрак;
- обед;
- ужин;
- перекусы;
- итог за день.

Для каждого приёма пищи:

- продукты;
- массу/порцию;
- калории;
- белки;
- жиры;
- углеводы.

Итог дня:

- суммарные КБЖУ;
- целевые КБЖУ;
- остаток;
- визуальный прогресс без агрессивной "красной" индикации небольшого превышения.

---

# 7. Собственная модель продуктов

Продукты не должны быть жёстко привязаны к конкретному внешнему API.

Спроектировать нормализованную доменную модель.

Минимально необходимая информация для продукта:

- id;
- название;
- бренд, если применимо;
- штрихкод, если применимо;
- энергетическая ценность;
- белки;
- жиры;
- углеводы;
- клетчатка, если данные доступны;
- размер стандартной порции, если применимо;
- единица измерения;
- источник данных;
- внешний идентификатор источника, если применимо;
- признак пользовательского продукта;
- владелец пользовательского продукта;
- статус/уровень доверия к данным;
- created_at;
- updated_at.

Конкретные названия таблиц и полей определить после анализа существующей модели проекта.

Не создавать дублирующую сущность, если подходящая модель уже существует.

# 8. Типы продуктов

## 8.1. Системные базовые продукты

Примеры:

- куриная грудка;
- яйцо;
- рис;
- гречка;
- овсяные хлопья;
- картофель;
- молоко;
- творог;
- говядина;
- банан;
- яблоко.

Это должна быть собственная контролируемая база базовых продуктов.

Не заполнять её случайными значениями из блогов и поисковой выдачи.

Для исходного наполнения использовать только надёжные открытые таблицы пищевой ценности с допустимой лицензией.

Перед импортом:

1. определить источник;
2. проверить лицензию;
3. задокументировать источник;
4. привести данные к единому формату;
5. обеспечить воспроизводимый импорт.

Если надёжный лицензируемый источник нельзя выбрать в рамках задачи - реализовать архитектуру и import pipeline, но не заполнять БД сомнительными данными.

## 8.2. Брендированные продукты

Например магазинные товары со штрихкодом.

Для них может использоваться Open Food Facts как дополнительный источник.

## 8.3. Пользовательские продукты

Пользователь должен иметь возможность создать собственный продукт:

- название;
- КБЖУ на 100 г или на порцию;
- размер порции;
- штрихкод при необходимости.

Пользовательский продукт по умолчанию должен быть приватным для создавшего его пользователя, если существующая модель проекта не предполагает иной безопасной схемы.

# 9. Open Food Facts

Рассматривать Open Food Facts как дополнительный, а не единственный источник.

Перед реализацией обязательно проверить актуальную официальную документацию:

- API;
- rate limits;
- требования User-Agent;
- лицензию;
- требования атрибуции;
- правила кэширования;
- ODbL/share-alike implications.

Не полагаться на значения лимитов из текста этой задачи - проверить актуальные значения самостоятельно.

## Архитектура

Пример логики:

```text
User search
    |
    v
Local database
    |
    +-- found --> return local result
    |
    +-- not found --> optional external provider
                           |
                           v
                    Open Food Facts
```

Создать абстракцию поставщика продуктов, чтобы Open Food Facts можно было:

- отключить;
- заменить;
- дополнить другим источником;

без переписывания доменной логики питания.

Например концептуально:

```text
FoodProvider
    - search(...)
    - get_by_barcode(...)
```

Конкретный интерфейс определить в соответствии с архитектурой проекта.

## Важное лицензионное требование

Не смешивать автоматически внешнюю ODbL-базу и собственные приватные данные так, чтобы возникали неочевидные лицензионные последствия.

Если необходимо - хранить:

- provenance/source metadata;
- атрибуцию;
- внешние данные логически отдельно от пользовательских/внутренних.

Решение и его обоснование задокументировать.

---

# 10. Поиск продуктов

Поиск должен быть быстрым и удобным на мобильном устройстве.

Приоритет выдачи:

1. недавно использованные;
2. избранные;
3. собственные продукты пользователя;
4. локальные системные продукты;
5. локально доступные брендированные продукты;
6. внешний источник при необходимости.

Нужны:

- debounce;
- минимальная длина поискового запроса;
- отмена устаревших запросов;
- отсутствие запроса на каждый введённый символ;
- нормальная обработка медленного/недоступного внешнего API.

Пользователь должен иметь возможность использовать пищевой дневник даже при недоступности Open Food Facts.

---

# 11. Недавние и избранные продукты

Добавить:

- недавно использованные продукты;
- избранные продукты;
- часто используемые продукты, если это можно корректно вывести из истории без лишней сложности.

Это должно ускорять добавление еды.

---

# 12. Повтор приёмов пищи

Поддержать быстрые сценарии:

- повторить продукт;
- скопировать приём пищи;
- скопировать весь день;
- повторить вчерашний завтрак/обед/ужин.

Перед копированием пользователь должен понимать:

- откуда копируются данные;
- на какую дату;
- какой приём пищи будет изменён.

Не создавать скрытых дублей при повторном нажатии.

---

# 13. Собственные блюда и рецепты

Пользователь должен иметь возможность собрать блюдо из продуктов.

Пример:

```text
Омлет
- яйцо 100 г
- молоко 50 г
- сыр 30 г
```

Система должна:

- рассчитать общий вес;
- рассчитать общие КБЖУ;
- рассчитать КБЖУ на 100 г;
- позволить добавить произвольную массу готового блюда в дневник.

Учитывать потерю/добавление массы при приготовлении только если пользователь явно задаёт итоговый вес блюда.

Не пытаться автоматически угадывать изменение массы от готовки.

---

# 14. Штрихкод

Добавить возможность поиска продукта по штрихкоду.

Приоритет:

1. локальная БД;
2. внешний бесплатный provider, если включён;
3. предложение создать пользовательский продукт, если ничего не найдено.

## Сканирование

Для Web/Mobile Web/Telegram Mini App изучить современный браузерный способ сканирования камерой.

Предпочитать:

- стандартный Barcode Detection API, если он поддерживается;
- лёгкую клиентскую библиотеку как fallback только при необходимости.

Не подключать платный Barcode API.

Обязательно предусмотреть:

- запрос разрешения камеры;
- отказ пользователя;
- отсутствие камеры;
- неподдерживаемый браузер;
- ручной ввод штрихкода.

Telegram Mini App не должен требовать отдельной серверной реализации сканирования.

---

# 15. Порции и единицы измерения

Пользователь должен иметь возможность вводить продукт понятно, без знания внутренних единиц.

Минимально:

- граммы;
- миллилитры, когда это корректно;
- стандартная порция, если она определена.

Пересчёт КБЖУ должен быть детерминированным и тестируемым.

Не добавлять произвольные бытовые меры вроде "ложка" или "стакан", если для конкретного продукта нет надёжного веса такой меры.

---

# 16. Тренировки

Не переписывать существующий тренировочный модуль.

Проверить текущие возможности и расширить только недостающее.

Целевое состояние:

- программы;
- календарь тренировок;
- выполнение;
- история;
- рабочий вес;
- повторения;
- подходы;
- личные рекорды;
- техника выполнения;
- тренировочный объём;
- прогресс нагрузки.

Если RPE/RIR ещё отсутствуют, оценить возможность их добавления.

Предпочтительнее RIR как более понятный формат для пользователя:

- 0 - повторов в запасе нет;
- 1;
- 2;
- 3;
- 4+.

Добавление RIR не должно усложнять базовый сценарий новичка.

Поле может быть необязательным.

---

# 17. Аналитика тренировок

В разделе прогресса постепенно поддержать:

- изменение рабочих весов;
- личные рекорды;
- объём по упражнению;
- объём по мышечной группе только если классификация упражнений позволяет делать это корректно;
- частоту тренировок;
- выполнение запланированных тренировок.

Не создавать псевдонаучные показатели без понятной формулы.

Все производные метрики должны иметь:

- формулу;
- единицы;
- тесты;
- понятное описание.

---

# 18. Раздел "Прогресс"

Объединить существующие данные прогресса в понятную структуру.

## Тело

- вес;
- замеры;
- фотографии, если уже поддерживаются или будут реализованы отдельной задачей.

## Питание

- средняя калорийность;
- средние Б/Ж/У;
- соблюдение целей;
- тренд.

## Тренировки

- частота;
- объём;
- PR;
- прогресс по выбранным упражнениям.

## Периоды

Минимально:

- 7 дней;
- 30 дней;
- 90 дней;
- произвольный период только если это не усложняет UX без необходимости.

Графики должны корректно работать при:

- отсутствии данных;
- одном значении;
- пропусках;
- длинной истории.

---

# 19. Соблюдение плана

Добавить отдельный слой аналитики adherence/compliance, но в интерфейсе использовать понятное русское название:

`Соблюдение плана`

Не использовать термин adherence в пользовательском UI.

Пример недельного отчёта:

```text
Тренировки: 4 / 4
Кардио: 2 / 3
Калории: 6 / 7 дней
Белок: 7 / 7 дней
Общее соблюдение: 91%
```

## Важно

Не придумывать формулу общего процента без обоснования.

Сначала определить:

- какие показатели действительно входят;
- одинаковый ли у них вес;
- как учитывать отсутствие цели;
- как учитывать день без запланированной тренировки;
- как учитывать неполный текущий день;
- что считать соблюдением калорий;
- какой допустимый диапазон использовать.

Формулу оформить отдельной domain/service-функцией и покрыть unit-тестами.

В документации объяснить выбранную модель.

# 22. Режим тренера

Все новые endpoint'ы должны учитывать роли и ownership.

Обязательно добавить негативные тесты доступа:

- пользователь не видит чужое питание;
- пользователь не видит чужие пользовательские продукты;
- тренер не видит клиента, который за ним не закреплён;
- бывшая связь тренер-клиент не даёт бессрочный доступ, если текущая бизнес-логика предполагает отзыв доступа.

# 43. Главный принцип

Не стремиться сделать "клон FatSecret + Fitness Online".

Нужно развить существующий Your Fitness Coach как самостоятельный продукт:

```text
Your Fitness Coach
        |
        +-- Сегодня
        |
        +-- Питание
        |
        +-- Тренировки
        |
        +-- Прогресс
        |
        +-- Тренер
        |
        +-- Профиль
```

Ключевое преимущество должно быть не в количестве экранов, а в том, что питание, тренировки, параметры тела и работа с тренером существуют в одной согласованной системе данных.

В дальнейшем поверх этой системы можно будет отдельно построить ИИ-ассистента, но текущий этап должен сначала создать качественный, независимый от платных API фундамент.
